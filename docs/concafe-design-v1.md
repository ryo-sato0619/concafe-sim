## 1. 全体構成

### 1.1 レイヤ分離

```
┌─────────────────────────────────────────┐
│  Presentation  (MonoBehaviour / UI)     │  Unity 依存
├─────────────────────────────────────────┤
│  Simulation    (純 C#、Unity 非依存)     │  ← テスト対象の本体
├─────────────────────────────────────────┤
│  Data          (バランス定数 JSON)       │
└─────────────────────────────────────────┘
```

**Simulation 層は `UnityEngine` を一切参照しない。** 理由は 3 つ。

1. EditMode テストが高速に回る（Play モードの起動が要らない）
2. 10 年 480 ターンの通し実行をテストで自動化できる
3. バランス調整のため何千回もシミュレートする必要があり、描画を挟めない

このゲームは数値モデルが本体であり、そこにバグやバランス崩壊があると
UI をどれだけ作り込んでも成立しない。分離は最優先事項である。

### 1.2 プロジェクト構成

```
concafe-sim/
├─ Assets/
│  ├─ Scripts/
│  │  ├─ Simulation/          ← 純 C#。noEngineReferences: true
│  │  │  ├─ Concafe.Simulation.asmdef
│  │  │  ├─ Json/             （最小の JSON リーダ）
│  │  │  ├─ Balance/          （定数の型付けと妥当性検査）
│  │  │  ├─ Model/            （Cast, Shop, Inventory, Weather, ...）
│  │  │  ├─ Rules/            （来客・注文・疲労・成長・判定）
│  │  │  └─ Random/           （GameRandom, RandomStreams）
│  │  ├─ Presentation/        ← MonoBehaviour / UI
│  │  ├─ Save/
│  │  └─ Editor/
│  │     ├─ SceneBuilder.cs   （シーンをコードから生成）
│  │     └─ BuildTool.cs      （batchmode ビルド）
│  ├─ Resources/
│  │  ├─ Data/
│  │  │  ├─ balance.json      ← すべての数値定数
│  │  │  ├─ easter_eggs.json  ← 源氏名イースターエッグ
│  │  │  ├─ careers.json      ← OB 進路 10 種
│  │  │  └─ names.json        ← 源氏名の自動生成候補
│  │  └─ Sprites/Parts/       ← ドット絵パーツ

├─ tools/

```

### 1.3 Simulation 層の隔離はコンパイラが強制する

`Concafe.Simulation.asmdef` に `"noEngineReferences": true` を置いている。
Simulation 層のどこかに `using UnityEngine;` を書くと、
**レビューを待たずにビルドが落ちる**（`error CS0246`）。

不変条件 9 は口約束ではなく、機械が守る。`Debug.Log` を 1 行足した時点で
CI が赤くなるため、気づかないうちに依存が入り込むことがない。

JsonUtility も使えないため、`Simulation/Json/` に最小の JSON リーダを持つ。
balance.json が扱う範囲（オブジェクト・配列・数値・文字列・真偽・null）だけの
実装で、規格の完全な実装ではない。

シーンは `Main.unity` **1 つだけ**とする。画面遷移は UI の差し替えで行う。
`three-months-of-spring` と同じ方式。シーンファイルの手編集による
レビュー不能な差分を発生させない。

## 2. 時間モデル

| 単位 | 定義 |
|---|---|
| 1 ターン | 1 週間（7 日） |
| 1 ヶ月 | 4 週 |
| 1 年 | 48 ターン（12 ヶ月 × 4 週） |
| 1 ゲーム | 480 ターン（10 年）＋ エンドレス |

```csharp
readonly struct GameWeek {
    public int AbsoluteWeek { get; }      // 0 起点の通算週
    public int Year   => AbsoluteWeek / 48;          // 0〜9
    public int Month  => (AbsoluteWeek % 48) / 4;    // 0〜11
    public int WeekOfYear => AbsoluteWeek % 48;      // 0〜47
}
```

**加齢は誕生週を跨いだ瞬間に行う。** キャストは `BirthWeekOfYear`（0〜47）を持ち、
`WeekOfYear` がそれに一致した週の冒頭で 1 歳加算する。
全員が同時に誕生日を迎えると 20 歳覚醒が一斉に起き、
「あと 3 週で覚醒する子を今飛ばすわけにいかない」という緊張が消える。

## 3. データモデル

### 3.1 キャスト

```csharp
sealed class Cast {
    public string Id;                  // ULID 相当の一意 ID
    public string StageName;           // 源氏名（プレイヤー入力）
    public int    Age;
    public int    BirthWeekOfYear;     // 0〜47
    public int    HiredWeek;           // 採用した通算週

    public Stats  Current;             // 現在値 0〜100
    public Stats  Cap;                 // 個体別の成長上限 0〜100
    public Stats  GrowthRate;          // 成長率の倍率（既定 1.0）

    public int    StaminaTier;         // 1〜5。固定。成長しない
    public double Fatigue;             // 現在の疲労蓄積

    public int    ScandalResist;       // 隠し 0〜100。生成時に決まる
    public double Trust;               // 隠し 0〜100。ケアでのみ増える。初期ほぼ 0
    public long   LifetimeSalesYen;    // 生涯売上（レポートと殿堂入り判定に使う）

    public Appearance Look;            // パーツ合成の組み合わせ
    public string EasterEggId;         // 該当なしは null
}

struct Stats {
    public double Regulars;  // 集客
    public double Fame;      // 知名度
    public double Talk;      // トーク
    public double Alcohol;   // 酒耐性
    public double Looks;     // ルックス
    public double Morale;    // モラル

    public double this[StatKind kind] { get; set; }   // 成長処理用
}
```

**`Cast` に疲労限界の実数値フィールドを持たせない。** 持たせると
「イベントで少し上げる」といった改変が書けてしまい、不変条件 1 が破れる。

## 4. 数値モデル

すべての係数は `balance.json` に外出しする。以下の式中の `k_*` は定数を指す。

### 4.1 来客数（1 日）

```
looksMul(c)   = 1.0 + (c.Looks / 100) * 0.2                    // 1.0〜1.2

regulars      = Σ_出勤 c.Regulars
fameRaw       = Σ_出勤 (c.Fame * looksMul(c))

visitors = floor( (regulars * k_regularBase
                  + fameRaw * k_fameBase * weatherFameFactor)
                  * stormFactor )
```

| 天候 | `weatherFameFactor` | `stormFactor` |
|---|---|---|
| 晴れ | 1.0 | 1.0 |
| 曇り | 0.8 | 1.0 |
| 雨 | **0.25** | 1.0 |
| 台風 / 大雪 | 0.1 | **0.1** |

**係数を 2 つに分けているのは意図的である。**

- 要件「集客は天候に影響されない」→ 雨では `stormFactor = 1.0` なので固定客は減らない
- 要件「台風/大雪は客がほぼ来ない」→ `stormFactor` で固定客ごと潰す

1 つの係数で済ませると、どちらかの要件が必ず破れる。

Web マーケター OB は `weatherFameFactor` を 1.0 側に引き上げる（`stormFactor` は触らない）。

### 4.2 来客の割り振り

各来客は出勤キャストの誰か 1 人に紐づく（指名）。
**固定客は指名先が固定される。** ここが離脱時の損失の根拠になる。

実装では固定客と新規客を別々に数える。

```
固定客   : キャストごとに floor(c.Regulars * k_regularBase * stormFactor) 人
新規客   : floor(Σ(c.Fame * looksMul(c)) * k_fameBase * fameFactor * stormFactor) 人を
           c.Fame * looksMul(c) の重みで配分する
```

固定客をキャストごとに切り下げるのは、「誰の客か」を曖昧にしないためである。
合計から按分すると、離脱で失う固定客の数が配分の都合で変わってしまう。

4.1 の式は合計としては同じ値になる（キャスト 3 人・各パラメータ 20 で 18 人/日。
T-44 で固定してある）。

### 4.3 売上の土台 — チャージと客のドリンク

売上の土台は**チャージ（席と時間の対価）と客のドリンク**である。

```
滞在 1 時間ごとに:  チャージ 1,100 円 ＋ 客のドリンク 900 円 = ちょうど 2,000 円 / 時間
```

| 内訳 | 売価 | 原価 | 備考 |
|---|---|---|---|
| チャージ | 1,100 | **0** | 席と時間の対価。全額が粗利 |
| 客のドリンク | 900 | 80（ソフト）／150（アルコール） | 売価は一律。原価だけが違う |

**どちらもキャストへのバックは付かない**（不変条件 25）。
店の売上であり、キャストが取ってきたものではない。

確率判定は行わない。ソフトドリンク／アルコールの消費量が滞在時間に比例して
確定するため、**発注量を来客予測から逆算できる**。発注がギャンブルではなく計算になる。

客のドリンクは**アルコールとソフトドリンクのどちらでもよく、あるものから出す。**
在庫があるほうを使い、両方無ければ機会損失になる。

**担当キャストの年齢は関係しない。** 年齢制限の対象はキャストが口にする
キャストドリンクと、キャストが付くボトルだけである（企画書 3.1）。
客のドリンクまで品目を分けると、未成年中心のシフトのときに
ソフトドリンクを切らしただけで売上が止まってしまう。

**チャージは在庫が切れていても入る。** 席と時間の対価であり、商品ではない。
在庫切れで失うのはドリンクぶんだけである。この区別があるため、
在庫を切らしても店は即死せず、機会損失として効いてくる。

### 4.3.1 滞在時間はトークで伸びる

```
延長確率 = k_extendBase + (c.Talk / statMax) * k_extendTalk
滞在は 1 時間から始め、1 時間ごとに延長判定。k_maxStayHours で打ち切る。
```

| トーク | 延長確率 | 期待滞在時間 |
|---|---|---|
| 0 | 0.15 | 1.18 時間 |
| 100 | 0.60 | 2.18 時間 |

**これによりトークの役割が明確になる。**

| ステータス | 役割 |
|---|---|
| 集客・知名度 | **何人来るか** |
| トーク | **1 人からいくら取れるか** |

トークは滞在時間を伸ばし、チャージとドリンクの回数を増やし、
さらにチェキ・キャストドリンク・ボトルの判定回数も増やす。
実測では客単価がトーク 10 で 3,786 円、トーク 90 で **12,999 円**になる（3.4 倍）。

**疲労は接客人数ではなく接客した延べ時間に比例する。**
長く座らせるほど疲れるため、トークを伸ばすと売上と引き換えに寿命が縮む。
「育てるほど失う」を数式に落としたのがこの二面性である。

### 4.3.2 追加の注文（滞在 1 時間ごとに判定）

```
talkF(c) = 0.5 + (c.Talk / 100)                                // 0.5〜1.5

P(チェキ)           = k_cheki  * talkF(c) * looksMul(c)
P(キャストドリンク)  = k_drink  * talkF(c) * looksMul(c)
P(ボトル)           = k_bottle * talkF(c)                       // ★ looksMul を掛けない
```

ボトルにルックス倍率を掛けないのは要件由来の制約である（不変条件 2）。

**未成年（18〜19 歳）の担当客**

| 本来の注文 | 変換後 |
|---|---|
| キャストドリンク（アルコール） | ソフトドリンク |
| アルコールボトル | **ノンアルコールボトル** |
| 客が自分で飲むドリンク | **変換しない。制限の対象外** |

企画書原文「お酒（キャストドリンク、各種ボトル）の注文がシステム的にロックされ、
**ノンアルコール等に変換される**」に従う。ボトルの注文自体は発生する。

**列挙されているのはキャストが口にするものだけである。** 客の飲み物は含まれない。

年齢制限がジレンマとして機能するのは、変換先のノンアルコールが
**段階数も上限額も劣る**ためである（14.2）。禁止によってではなく、
上限の低さによって制限を成立させる。

### 4.3.3 ボトルの段階選択

ボトルは単一商品ではなく段階を持つ（14.2）。どの段階が注文されるかは、
担当キャストの能力で**解禁された段階の中から一様に抽選**する。

```
tierPower(c) = (c.Talk * 0.6 + c.Alcohol * 0.4) / 100     // 20 歳以上
tierPower(c) =  c.Talk / 100                              // 未成年（酒耐性を参照しない）
```

`tierPower` が段階ごとの解禁値以上なら、その段階が抽選対象に入る。
段階 1（最安）は常に解禁されている。

**この式が「20 歳の覚醒」の正体である。** 未成年の間は酒耐性が `tierPower` に
寄与しないため、どれだけ酒耐性を溜めても高額ボトルが開かない。
20 歳になった瞬間に酒耐性が乗り、解禁段階が跳ね上がる。

| 状態 | `tierPower` | 解禁される段階 | 期待単価 |
|---|---|---|---|
| トーク 80 の未成年 | 0.80 | ノンアル 12,000 / 35,000 | 23,500 円 |
| 20 歳になり酒耐性 60 が乗る | 0.72 | アルコール 12,000〜110,000 | 56,750 円 |

`tierPower` の数値そのものは下がっているのに期待単価が 2.4 倍になる。
アルコール側の段階が密で上限が高いためである。

一様抽選は v1 の暫定仕様である。段階 5 の通しシミュレーションで
実測してから重み付けを検討する。抽選の偏りを先に作り込むと、
どの数値が効いているのか切り分けられなくなる。

**解禁されていない段階のボトルは、仕入れても絶対に売れない。**
発注 UI は、現在のロスターで販売可能な段階を明示すること（第 8 章）。

#### 期間限定商品（U-18 決着）

`k_limited = 0.12`。他の品目と同じく滞在 1 時間ごとに判定し、
トーク係数が掛かる。ルックス倍率は掛けない（不変条件 2）。

**ただし 1 点だけ他の品目と扱いが違う。在庫が無くても機会損失にしない。**

在庫切れを損として数えると、実質「毎週必ず仕入れる商品」になる。
そうなると発注の手が 1 つ減り、**「限定」という性格が消える。**
在庫があるときの上振れとして置いてある。

実家の家業 OB がいると**原価 0 で週 8 個届く**（6.1）ので、
その OB がいる間は純粋な上乗せになる。バックの対象にはしない（不変条件 25）。
冷蔵しないので冷蔵庫の上限（14.9）にも数えない。

### 4.4 在庫と機会損失

注文が発生した時点で在庫を 1 消費する。在庫が 0 のとき:

1. その売上は立たない
2. 機会損失としてカウントし、週末レポートに表示する
3. 担当キャストの `Regulars` を `k_lostRegular = 0.5` だけ減らす（常連の失望）

**U-05 決着: 3 を採用する。ただし 1 日 1 回までとする**（`stock.lostRegular`）。

機会損失 1 件ごとに削る素直な実装だと、繁盛している日ほど在庫切れの件数が
増えるため 1 日に数十件出ることがあり、**1 週間で固定客が消し飛ぶ**。
「発注を怠ると常連が離れる」という手触りを出すのが目的であって、
在庫管理を一度でも外したら店が終わる、という重さは意図していない。

**チャージは在庫が切れていても入る**（4.3）。在庫切れで失われるのは
ドリンク・チェキ・ボトルの売上だけである。

### 4.5 疲労

```
sober(c)   = max(0, 1 - c.Alcohol / 100)

酒疲労(c)  = ( キャストドリンク杯数(酒) * k_fatiguePerDrink
             + Σ_開けたアルコールボトル (段階番号 * k_fatiguePerBottleTier)
             ) * sober(c)

trustRelief(c) = 1 - (c.Trust / 100) * k_trustRelief      // 1.0 〜 0.65

dailyFatigue(c) = ( k_fatigueBase
                  + 接客数 * k_fatiguePerGuest
                  + 酒疲労(c)
                  ) * stormFatigueMul * trustRelief(c)
```

**`trustRelief` は疲労の蓄積速度にのみ掛かる。疲労限界値には一切触れない。**
限界値を上げる実装（`StaminaTier` の変更、限界値への加算、上限の一時解除）は
不変条件 1 に反する。信頼を積んだキャストは「限界が上がる」のではなく
「限界に届くのが遅くなる」。

`Trust` が増えるのは悩み相談を行ったときだけである。

```
悩み相談: Fatigue -= k_careRecover ;  Trust = min(100, Trust + k_trustPerCare)
```

**高額ボトルほど疲労が重い。** 段階番号（1〜6）に比例させることで、
400,000 円のボトルは 12,000 円の 6 倍の疲労を生む。

これにより酒耐性が二重の意味を持つ。高い段階を解禁する鍵であり、
同時にその段階を開け続けるための耐久力でもある。
酒耐性を伸ばさずトークだけで段階を上げたキャストは、
解禁された高額ボトルによって急速に消耗する。

**ノンアルコールボトルは酒疲労を生まない。** 未成年は接客疲労のみを負う。
単価は低いが長持ちする、というトレードオフになる。

`stormFatigueMul` は台風/大雪で 2.0、それ以外は 1.0（要件 5.2）。
休業日は疲労を `k_restRecover` だけ回復する。

疲労限界:

| Tier | 限界値 |
|---|---|
| 1 | 未決（U-06） |
| … | … |
| 5 | 未決（U-06） |

### 4.6 成長

出勤日の行動と、店長 AP による特訓で伸びる。

```
gain = baseGain * c.GrowthRate.<param> * (1 - c.Current.<param> / c.Cap.<param>)
c.Current.<param> = min(c.Cap.<param>, c.Current.<param> + gain)
```

上限に近づくほど鈍化し、**`Cap` を超えることは構造的にあり得ない**。
`Cap` は個体差の本体であり、実行時に書き換えない。

未成年の間も酒耐性は成長する（「機能しない」のは注文処理であって成長ではない）。
20 歳で解禁されたときに「溜め込んだ酒耐性が解放される」という要件 4.3 の
記述はこの挙動を指す。

### 4.7 スキャンダル判定（週末）

```
P(scandal) = k_scandalBase
           * (1 - c.ScandalResist / 100)
           * (1 + 週の酒注文数 * k_scandalPerDrink)
           * (1 - c.Morale / 100 * k_scandalMoraleGuard)
```

耐性が 100 なら絶対に炎上しない。0 なら常に最悪側に寄る（ニシキ）。

#### 炎上の結果（U-21）

| 項目 | 値 |
|---|---|
| 知名度 | **−25%** |
| 集客 | **−15%** |
| モラル | −10（実数） |
| そのまま退店 | 15% |

**削れるのは知名度・集客・モラルだけである。** トークと酒耐性は減らさない。
炎上は「客が引く」出来事であり、接客の技量そのものが失われるわけではない。

炎上して退店する場合は**飛ぶのと同じ扱い**にする（悪評が他のキャストの
固定客を削る）。不名誉な去り方だからである。
**放火は起きない。** 放火は疲労限界を超えたときだけの出来事である（6.3）。

損失の重さは調整の余地がある。当初 知名度 −50% / 集客 −30% にしたところ、
10 年を通せる出勤ペースが週 4 日だけに絞られてプレイヤーの選択が消えたため、
半分に緩めた（14.8）。

### 4.8 離脱判定（週末）

`c.Fatigue > 限界値` で離脱する。**去り方は 2 種類あり、キャストの市場価値で決まる。**

```
marketValue(c) = (c.Regulars + c.Fame + c.Talk) / 3

marketValue >= k_defectThreshold  → 転生（他店へ移籍）
それ未満                          → 飛ぶ（バックレ）
```

| | 飛ぶ | 転生 |
|---|---|---|
| ロスターから除外 | する | する |
| そのキャストの固定客 | 失う | 失う（移籍先についていく） |
| **他キャストへの波及** | **全員の `Regulars` を `k_antiSpread` だけ削る** | **なし** |
| 予兆 | なし（突然） | **あり** |
| OB 効果 | なし | なし |

**波及の有無が本質的な差である。** 飛ばれると悪評が広がって店全体の基礎来客が落ちる。
転生は痛いが、店には傷が残らない。

**育てたキャストほど、飛ばれるのではなく引き抜かれるようになる。**
`marketValue` はプレイヤーが伸ばしたパラメータそのものなので、
離脱の質が育成の結果として変化する。

#### 予兆

`c.Fatigue >= 限界値 * k_warnRatio` を満たしたキャストは、週末レポートに警告が出る。

| 対象 | 文言の方向 |
|---|---|
| 転生しうる（`marketValue` が閾値以上） | 「他店から声がかかっているらしい」 |
| 飛びうる | 「顔色が悪い」 |

予兆が出てからケアに AP を割けば間に合う。
**新人が飛ぶのは防ぎにくく、エースの転生は防げる。** この非対称は意図的である。
「売上を作るキャストほど、目をかけ続けないと持っていかれる」という状態を作る。

`Trust` は隠しパラメータだが、この予兆と、キャスト詳細画面の定性的な文言
（「この店を気に入っているようだ」等）によって、プレイヤーは手応えを得られる。
数値を見せずに投資の効果を伝える。

#### モラルによる猶予は設けない（U-07 決着）

「モラルが高いキャストは疲労限界を超えてもしばらく踏みとどまる」という
案を検討したが、**採らない。**

理由は不変条件 1 である。**延命は `trustRelief`（疲労の蓄積速度の低下）だけで
行うと決めてある。** 限界を超えてからの猶予は、名前を変えた限界値の引き上げに
ほかならない。一度これを認めると「イベントで少し」「設備で全体を」も
同じ論法で通ってしまい、疲労限界が事実上の可変パラメータになる。

**モラルはすでに 3 か所で効いている**ので、離脱にまで効かせる必要もない。

| モラルが効く先 | 効き方 |
|---|---|
| 卒業条件（4.9） | 45 未満で辞めると OB にならない |
| スキャンダル確率（4.7） | `(1 - モラル/100 × 0.5)` |
| ニシキの SNS イベント | 店舗全体のモラルを下げる |

疲労にまで効かせると、モラルが「全部に効く上位ステータス」になり、
ルックスに対して不変条件 2 が禁じているのと同じ形の崩れ方をする。

**疲れたキャストを救う手は、悩み相談（信頼度）とシフトの置き方の 2 つに限る。**
後者は U-20 のピークタイム（14.3.1）で成立するようになった。

### 4.9 卒業と進路

卒業条件（U-08 決着。`careers.json` の `graduation`）:

> 在籍 **96 週（2 年）以上** **かつ** `Morale >= 45`
> **かつ**（年齢 **24** 以上 **または** 全パラメータが `Cap` の 98% 到達）

モラルが閾値未満のまま退職した場合は**円満卒業とせず、OB 効果を残さない**
（不変条件 16）。モラルを「最重要ステータス」たらしめているのはこの分岐である。

#### モラル閾値を 70 → 45 に下げた（段階 5）

段階 4 では閾値を 70 にしていたが、通しシミュレーションで**卒業が 1 件も
起きなかった**。モラルの分布は中央 38 / 最大 57 で、70 に届く経路が無い。

- モラルが伸びる経路は**特訓しか無かった**。店長 AP は週 10 で、
  トーク・集客を伸ばしつつモラルにも回すと 1 人あたり年数回しか触れない
- 求人ティア 1 の `capMean` は 45 である。**上限そのものが閾値の下**にあり、
  安い求人で採ったキャストは構造的に卒業できない

2 つを同時に直した。

1. **出勤でモラルが自然成長する**（`manager.moraleWorkGainRatio = 0.5`）。
   トーク・知名度の伸びの半分の速さ。真面目に働き続ければ真面目さも育つ、
   という筋は通る。ただし伸びは遅いので、特訓とケアの価値は消えない
2. **閾値を 45 に下げた。** 求人ティア 1 の `capMean` と同じ水準である。
   「安いキャストでも、長く勤めれば卒業に届きうる」位置に置いた

結果、卒業は 0 → **4.2 回/run**（週 4 日・60 シード）になった。
モラルの最大値は中央 58 / 最大 78。閾値 70 のままだと今でもほぼ届かない。

**卒業は疲労限界の超過より先に判定する。** 設計書 3.3 は
「離職 → スキャンダル → 卒業」の順としていたが、それだと 2 年勤めて
モラルも高いキャストが疲労限界を超えた瞬間に「飛んだ」扱いになる。
育て上げた相手の結末を先に見るのが自然なので入れ替えた。

**卒業でも固定客は失われる。** ただし悪評は広がらない。

進路は `careers.json` で重み付け抽選する。重みはパラメータ / 100 に掛かる。

| 進路 | 重み | 店舗への効果 |
|---|---|---|
| アイドル | 知名度 1.2 / トーク 0.8 / ルックス 1.0 | 1 日店長（6%/週。売上 +35%） |
| 飲料卸売業者 | 集客 1.0 / モラル 0.4 | ドリンク原価 ×0.88 |
| 出版関係者 | モラル 1.0 / トーク 0.8 | 特訓本 0.5 個/週（AP 不要） |
| 衣装デザイナー | ルックス 1.4 | 店舗ルックス +4 |
| 腕利きのスカウトマン | 集客 0.8 / モラル 0.8 / 知名度 0.4 | 候補の成長上限 +5 |
| 心理カウンセラー | モラル 1.2 | 疲労回復量 ×1.25 |
| Web マーケター | 知名度 1.4 | 悪天候の知名度ペナルティ −30% |
| 酒造メーカー | 酒耐性 1.5 | 最高段階ボトル 0.4 本/週（原価 0） |
| 実家の家業 | モラル 0.3 | 期間限定商品 8 個/週（原価 0） |
| 玉の輿婚 | ルックス 1.0 / 知名度 0.6 | ご祝儀 80 万円（4%/週） |

**「どう育てたか」が進路に出る。** 酒耐性を伸ばせば酒造メーカー、
ルックスなら衣装デザイナー、知名度なら Web マーケターが最も出やすい
（T-40 で固定）。

#### OB 効果には上限がある

10 年で何人も輩出できるため、上限が無いと終盤で効果が暴走する。
`careers.json` の `caps` で頭打ちにしてある。

| 効果 | 上限 |
|---|---|
| ドリンク原価の倍率 | 0.55 以上 |
| 店舗ルックス | +18 まで |
| 疲労回復の倍率 | ×2.0 まで |
| 悪天候の軽減 | 75% まで |
| 候補の上限ボーナス | +18 まで |

**Web マーケターは `stormFactor` に効かせない。** 効かせると
「台風でも客が来る」ことになり、天候の係数を 2 つに分けた意味が崩れる（4.1）。

|---|---|---|---|
| 1 | 体 | 肌色 tint | body_a |
| 2 | 服 | 服色 tint | dress_a 〜 dress_e |

```
Assets/Resources/Sprites/Parts/<layer>/<id>.png
```

各レイヤ 5 種、色を 6 段階持たせるだけで数千通りの外見が作れる。
**モブがランダム生成される以上、個別に絵を描く選択肢は存在しない。**

### 5.2 仮グラフィックによるフォールバック

**パーツ PNG が 1 枚も存在しない状態でもゲームが最後まで動くこと。**
`PartSpriteProvider` は、該当 PNG が無い場合に単色矩形のプレースホルダを返す。

これは要件 8 の項目 8 に対応する。絵の完成を待つとバランス調整に着手できず、
バランスが決まらないと絵の必要点数も決まらない、というデッドロックに陥る。

### 5.3 表情

疲労段階・スキャンダル発生などに応じて口レイヤだけを差し替える。
`three-months-of-spring` の `CharacterSpriteProvider.FindSubstitute` と同様、
**表情 PNG が足りない場合は手持ちで代用**し、絵が消えないようにする。

### 5.4 技術仕様

| 項目 | 指定 |
|---|---|
| 形式 | PNG（Unity は WebP を読めない） |
| 背景 | 本物の透過（アルファチャンネル） |
| 想定サイズ | 1 体あたり 64×64 または 96×96 px |
| インポート | Point (no filter) / Compression: None / Pixels Per Unit 統一 |
| ピボット | 下端中央 |

インポート設定は `TextureImportRules.cs` が自動適用する。手作業を発生させない。
**Filter Mode を Bilinear のままにするとドット絵が滲む。** 自動化必須。

## 6. イースターエッグ（データ駆動）

`Assets/Resources/Data/easter_eggs.json`。**コードに名前を直接書かない**（不変条件 13）。

### 6.1 エッグの定義

```json
{
  "id": "nishiki",
  "enabled": true,
  "match": ["ニシキ", "にしき", "錦"],
  "revealOnHire": true,
  "hireMessage": "...",

  "growthRateMultiplier": { "all": 10.0, "alcohol": 0.0 },
  "fixedStaminaTier": 1,
  "fixedScandalResist": 0,

  "onDeparture": "burnDown",
  "burnDownOn": "any",
  "eventId": "nishiki_burn_down"
}
```

| フィールド | 既定 | 意味 |
|---|---|---|
| `enabled` | false | false なら一切マッチしない。空き枠はこれで止める |
| `match` | — | 完全一致の候補。前後の空白（全角含む）は無視 |
| `revealOnHire` | true | 採用直後に「何かが起きた」と見せるか |
| `statBonus` / `statMultiplier` | 0 / 1 | 初期値 |
| `capBonus` / `capMultiplier` | 0 / 1 | 成長上限 |
| `growthRateMultiplier` | 1 | 成長率 |
| `fixedStaminaTier` | 無指定 | 疲労限界の段階を固定（1〜5） |
| `fixedScandalResist` | 無指定 | 隠しパラメータを固定（0〜100） |
| `onDeparture` | none | `burnDown` で離脱の結末を差し替える |
| `burnDownOn` | any | `any` / `runAway` |
| `eventId` | null | 専用イベント。**未実装 ID でもゲームは止まらない** |

係数はすべて `all` で全体、個別キー（`regulars` / `fame` / `talk` / `alcohol` /
`looks` / `morale`）で上書きできる。適用順は

```
上限 = clamp((生成値 + capBonus) * capMultiplier, 1, statMax)
初期 = clamp((生成値 + statBonus) * statMultiplier, 0, 上限)
成長率 = 生成値 * growthRateMultiplier
```

上限を先に決めるのは、初期値が上限を超えられないためである。

「ニシキ」では `alcohol: 0.0` が `all: 10.0` を上書きするため、
**酒耐性だけが一切伸びない。**

疲労限界と隠しパラメータの固定は**生成時にのみ効く**。不変条件 1 が禁じているのは
「生成後の変動」であり、生成そのものはここで行われる。以後は誰も触らない。

### 6.2 空き枠

`enabled: false` かつ `match: []` のひな形を 3 つ置いてある。
それぞれ違う型の効果を書いてあるので、写して使える。

| id | 型 |
|---|---|
| `slot_stat_bonus` | 初期値特化（`statBonus` ＋ `statMultiplier` でデバフ） |
| `slot_cap_bonus` | 上限特化（`capMultiplier` ＋ 低い初期値 ＋ 高い耐久） |
| `slot_special_event` | 専用イベント（`fixedScandalResist` ＋ `eventId`） |

### 6.3 放火 — 離脱の結末を差し替える

```json
"events": [
  { "id": "nishiki_burn_down", "gameOver": "arson", "title": "...", "body": ["..."] }
]
```

疲労限界を超えて離脱するとき、`EasterEggRules.ResolveBurnout()` が結末を決める。

| 条件 | 結果 |
|---|---|
| エッグ無し、または `onDeparture: none` | 通常どおり飛ぶ／転生する |
| `burnDownOn: any` | 飛ぶ・転生のどちらでも放火 |
| `burnDownOn: runAway` | 飛ぶ側のときだけ放火。育て上げれば穏便に移籍する |
| **卒業** | **常に放火しない** |

卒業を除外しているのは、放火が「燃え尽きて店を去る」瞬間の出来事だからである。

**イベント定義が無くても結末は成立する。** `events` が空でも放火と強制終了は起きる。
イベントを書く前に名前だけ決められる状態を保つのは、空き枠のための仕様である
（不変条件 14 と同じ姿勢）。

### 6.4 採用後は ID で解決する

`Cast.EasterEggId` に採用時の判定結果を記録し、以後は**源氏名で引き直さない。**
JSON の `match` を書き換えても、すでに在籍しているキャストの挙動は変わらない。

### 6.5 空き枠は `enabled` だけで出し入れする

空き枠 3 つ（U-14）は中身が保留のまま `enabled: false` で止めてある。
**中身を決めた日に、JSON の 2 か所を直すだけで出せる状態を保つこと。**
コードの変更もビルドも要らない。

| やること | 手順 |
|---|---|
| 出す | `enabled` を `true` にして `match` に源氏名を入れる |
| 止める | `enabled` を `false` に戻す |

`enabled: true` のまま `match` が空だと**起動時に弾く。** 黙って通すと
「有効にしたのに一生発動しない」状態になり、実装を疑うことになる。

**止め直しても、すでに在籍しているキャストは自分のエッグを持ち続ける**（6.4）。
効果は採用の瞬間に焼き込まれている（不変条件 24）ので、後から取り上げると
進行中のセーブでそのキャストが別人になってしまう。

ひな形は空にしない。空のまま置くと、出したい日に結局コードから書き起こす
ことになる。3 枠とも動く形の定義が入っている（初期値特化 / 大器晩成 /
専用イベント持ち）。

### 6.6 ゲームオーバー

```csharp
enum GameOverReason { None, CashShortage, Arson }
```

どちらも**クリアランクを付けず、強くてニューゲームの初期資金ボーナスを与えない**
（要件 5.3.1）。バッドエンドが周回の近道になってはいけない。

## 7. セーブデータ

| 項目 | 方針 |
|---|---|
| 形式 | JSON |
| 置き場所 | `Application.persistentDataPath` |
| スロット | **手動 10 ＋ オートセーブ 1**（U-09 決着） |
| オートセーブ | 週末の決算完了時。**手動枠とは別枠**なので手動を潰さない |
| 乱数の状態 | **保存しない**（U-10 決着。12.1） |
| 跨ぐ情報 | 殿堂入り OB とクリアランクは別ファイル（`hall_of_fame.json`）に保存 |

**480 ターン分の履歴を全部保存しない。** 週次の集計値（売上・利益・来客数）だけを
折れ線グラフ用に残し、日次の明細は破棄する。

### 7.1 Simulation 層はファイルに触らない

`SaveCodec` は `GameState` と JSON 文字列を相互変換するだけで、保存先を知らない。
実際の読み書きは `ISaveStorage` の実装が引き受け、Presentation 層が差し込む。

Simulation 層に `System.IO` を持ち込むと WebGL で動かなくなるうえ、テストから
保存を差し替えられなくなる。`InMemorySaveStorage` があるので、
**セーブの往復は EditMode テストだけで検証できる。**

### 7.2 数値は往復できる形で書く

`JsonWriter` は小数を `R` 書式（往復を保証する書式）で書く。
丸めた表記で書き出すと、セーブしてロードしただけでパラメータがわずかに動く。
480 週を跨ぐゲームでその誤差が積もると、**セーブしたかどうかで結果が変わる。**
`SaveTests.キャストの値が丸められずに往復する` が誤差の許容なしで比較している。

## 9. 乱数

```csharp
sealed class GameRandom {
    public GameRandom(ulong seed);
    public ulong State { get; }   // セーブ可能
}
```

`UnityEngine.Random` を使わない。理由は 3 つ。

1. 静的状態のため、テストの並列実行で結果が汚染される
2. 状態をセーブできない
3. Simulation 層が `UnityEngine` を参照しない方針（1.1）に反する

用途ごとに独立したストリームを持つ（キャスト生成用・天候用・注文用）。
1 本の乱数列を共有すると、注文処理の呼び出し回数がわずかに変わっただけで
天候まで変わり、バランス調整時の比較ができなくなる。

## 11. 不変条件（実装禁止事項）

**一見合理的に見えて、設計の前提を壊す変更を列挙する。実装中に何度でも参照すること。**

1. **疲労限界を成長・変動させない。** `StaminaTier` は生成時に決まり、以後不変。
   「イベントで少し上げる」「設備投資で全体を上げる」も禁止。
   **信頼度・OB 効果・設備で限界値を上げるのも禁止**（延命は `trustRelief` による
   蓄積速度の低下だけで行う）。
   これを可変にすると、要件 1.1 の緊張が消えてゲームが単なる右肩上がりの育成になる

2. **ルックス倍率をボトル注文率に掛けない。** 掛けるとルックスが全ステータスの
   上位互換になり、トーク・酒耐性・モラルの存在意義が消える

3. **未成年（18・19 歳）のキャストに酒を口にさせない。**
   キャストドリンクはソフトドリンクへ、アルコールボトルは**ノンアルコールボトルへ変換**する。

   **対象はキャストが飲むものだけである。客が自分で飲むドリンクは制限しない。**
   企画書が挙げているのは「キャストドリンク、各種ボトル」であり、
   客のドリンクは含まれない。ここを縛ると、未成年中心のシフトで
   ソフトドリンクを切らしただけで売上が止まる（4.3）

4. **未成年の `tierPower` に酒耐性を算入しない。**
   ここを入れると 20 歳の覚醒が消え、年齢制限が単なる減点になる。
   ノンアルコールボトルの段階を増やす／解禁条件を緩めることも同様に禁止。
   **年齢制限は「売らせない」ことではなく「上限が低い」ことで成立している**（4.3）

5. **解禁されていない段階のボトルを注文させない。** `tierPower` の判定を
   迂回する経路（イベント、OB 効果、在庫があるから売れる等）を作らない。
   高額ボトルは育成の到達点であり、そこが崩れると育成の報酬が消える

6. **店長のレベルアップ要素を作らない。** 店舗強化は資金による設備投資のみ。
   店長が育つと、キャストの世代交代という主題が薄まる

7. **店長 AP の週次付与量を店舗規模に応じて増やさない。**
   終盤に全員をケアできなくなることが「使い潰すか伝説にするか」の圧力源である。
   緩和は OB 効果（心理カウンセラー・出版関係者）に限る

8. **金額はすべて整数（円）。** `long` で保持する。`float` / `double` を使わない。
   480 ターンの累積で誤差が可視化される

9. **`UnityEngine` を Simulation 層から参照しない。** `Debug.Log` も含む。
   テストの高速実行とバランス調整の自動化が成立しなくなる

10. **数値定数をコードに直接書かない。** すべて `balance.json` に置く。
    バランス調整のたびに再コンパイルが必要になると、調整回数が 1 桁減る

11. **`UnityEngine.Random` を使わない。** `GameRandom` のみ（第 9 章）

12. **キャストの `Cap` を実行時に書き換えない。** 個体差の本体であり、
    ここが動くと「当たり個体を引く」というゲーム性が消える

13. **イースターエッグの名前をコードに書かない。** `easter_eggs.json` のみ

14. **絵が無い状態で落ちる作りにしない。** パーツ PNG が 0 枚でも
    最後まで通しでプレイできること（要件 8-8）

15. **シーンを手で編集しない。** `SceneBuilder.cs` からコードで生成する。
    手編集の差分はレビューできない

16. **卒業条件を満たさない退職に OB 効果を与えない。** モラルの価値が消える

17. **信頼度を生成時のランダム値にしない。** 初期はほぼ 0 で、
    **悩み相談によってのみ増える。** 素質にすると「当たり個体を引く」話になり、
    ケアという行動の価値が消える

18. **信頼度を減衰させない。** 貯金として設計されている。
    減衰させるとケアが投資ではなく維持義務になり、
    「誰に関係を積むか」という選択が「全員を回し続ける作業」に変わる

19. **転生に悪評の波及（`k_antiSpread`）を付けない。** 飛ぶとの差はここにしかない。
    両方に付けると、育成によって離脱の質が変わるという設計が消える

20. **飛ぶ側に予兆を出さない。** 予兆が転生にしか出ないことが、
    「売上を作るキャストほど目をかけ続ける必要がある」という圧力を作っている

21. **バッドエンドに初期資金ボーナスを与えない。** 資金ショートも放火も同じ。
    バッドエンドが周回の近道になると、丁寧に 10 年を回す動機が消える

22. **卒業で放火させない。** 放火は燃え尽きて店を去る瞬間の出来事であり、
    円満に辞めた相手が火を点けることはない

23. **採用後のキャストを源氏名で引き直さない。** `Cast.EasterEggId` で解決する。
    JSON を書き換えるたびに在籍中のキャストが化けると、セーブデータが壊れる

24. **イースターエッグで `Cap` を生成後に書き換えない。** 適用は採用の瞬間のみ。
    以後は不変条件 12 の対象に戻る

25. **バックの対象をチャージと客のドリンクに広げない。** 席と時間の対価は店の売上である。
    広げると、トークを伸ばしてもバック対象の比率が変わらなくなり、
    「エースの人件費が売上に連動して跳ね上がる」という設計が消える（14.3）

26. **来客・自然成長を出勤日数で数えない。出勤時間で数える。**
    シフトを時刻で持つ意味が無くなり、「短く入れる」という選択が消える

### 12.1 リロードで結果が変わる（U-10 決着）

**乱数の状態をセーブに含めない。リセマラを許容する。**

ロードのたびに `SaveCodec.Decode` へ新しい種を渡す。同じセーブから何度
やり直しても、注文・イベント・炎上・離脱・求人の質はすべて引き直される。

含めない側を選んだのは、このゲームが**取り返しのつかなさで緊張を作っていない**
からである。疲労限界も離脱も、プレイヤーの選択（出勤時間・ケアの配分・
求人への投資）の結果として来る。運の 1 回に賭けさせる設計ではない以上、
やり直しを禁じても苦味が増えるだけで、判断の質は上がらない。

#### ただし、その週の天候と予報だけは保存する

週頭に予報を見せてからシフトを組ませている（5.2）。ロードで天候まで
引き直すと、**プレイヤーが見た予報が後出しの嘘になる。**
引き直るのは予報より後だけ、という線を引いてある。

| ロードで | |
|---|---|
| 変わらない | その週の天候・予報、資金、在籍キャスト、設備、在庫、OB |
| 変わる | 注文・専用イベント・炎上・離脱・求人で届く候補の質 |

#### 決定性そのものは失っていない

種を渡す形にしてあるので、同じ種を渡せば同じ展開になる。
通しシミュレーション（`AutoPilot`）もテストもここに依存している。
**非決定性の源は Simulation 層の外にある**（呼び出し側が毎回違う種を渡す）。

これを実装で崩さないよう、`SaveTests.セーブに乱数の状態が書かれていない` が
セーブの本文を検査している。状態を書き始めたらそこで落ちる。

## 14. バランス初期値（暫定 / 2026-09-22）

`balance.json` の初期値。**段階 5 の通しシミュレーションで調整する前提の叩き台**であり、
確定値ではない。ここを動かしても他の設計は壊れない（不変条件 7 の目的）。

### 14.1 資金と経費（U-01 / U-17）

| 項目 | 値 |
|---|---|
| 初期資金 | 1,500,000 円 |
| 引き継ぐキャスト | **2 人**（ミク・サクラ） |

#### 経費は 3 本立て

| 項目 | 値 | 性質 |
|---|---|---|
| 家賃・光熱費・通信費 | 70,000 円/週（月 28 万） | 固定 |
| 枠拡張ぶんの家賃 | ＋25,000 円/週 × 拡張回数 | 固定 |
| 店長の報酬 | 60,000 円/週（月 24 万） | 固定 |
| その他経費 | **売上の 26%** | **変動** |

「その他経費」は決済手数料・消耗品費・広告宣伝費・雑費である。

**固定を薄く、変動を厚くしているのが要点である。** 理由は 2 つ。

1. 全部を固定にすると、売上が伸びたぶんがそのまま利益になり、終盤が緩くなる。
   変動費があることで**規模が大きくなっても利益率が保たれる**
2. キャストが欠けたときに経費も一緒に下がる。固定が重いと
   1 人失った時点で立て直せなくなり、リカバリーの余地が消える

v1.0 では「固定費 93,000 円」の 1 本だけで、家賃以外の経費と店長の報酬が
まるごと抜けていた。そのため序盤の利益率が 37% という飲食業ではあり得ない
水準になっていた（14.8）。

#### 前任者から引き継ぐキャスト

**空の店から始めない。** 売上が無いまま家賃と店長報酬だけが出ていき、
求人・採用・育成が回り出す前に資金が尽きる。
企画書の「赤字寸前のコンカフェ店長となり」は、
すでに動いている店を引き継ぐという意味である。

引き継ぐキャストは求人ティア 1 で生成し、初期値に +15 する
（前任者がある程度育てている）。名前は `shop.initialCastNames` で変えられる。

**店舗拡張で固定費が上がる**のが重要である。枠を増やすこと自体がリスクになり、
「広げたが埋められない」という失敗を成立させる。

### 14.2 商品（U-02）

#### チャージと滞在

| 項目 | 値 |
|---|---|
| チャージ | **1,100 円 / 滞在 1 時間**（原価 0） |
| 客のドリンク | **900 円**（原価のみ引く） |
| 合計 | **ちょうど 2,000 円 / 時間** |
| 滞在の上限 | 4 時間（かつシフト時間以内） |
| 延長確率 | `0.15 + (トーク / 100) × 0.45` |

チャージは在庫に依存せず、席と時間の対価として必ず入る（4.3）。

#### 在庫品目

| 品目 | 原価 | 売価 | 備考 |
|---|---|---|---|
| ソフトドリンク | 80 | **持たない** | 客のドリンク 900 かキャストドリンク 1,600 として売れる |
| アルコール | 150 | **持たない** | 同上 |
| チェキ用フィルム | 120 | **1,600** | 切らすと最大の機会損失 |

ソフトドリンクとアルコールに売価を持たせないのは意図的である。
**同じ在庫が用途によって違う値段で売れる**ため、品目に売価を貼ると二重定義になる。
検査もこれを強制し、`priceYen` を書くと弾かれる。

#### キャストドリンク

独立した在庫を持たず、**注文種別**として扱う。売価は年齢によらず **1,600 円**。

| 注文 | 消費する在庫 |
|---|---|
| キャストドリンク（20 歳以上） | アルコール 1 |
| キャストドリンク（未成年） | ソフトドリンク 1 |

価格を年齢で分けないのは、この商品の対価がキャストの同席時間であり、
中身の液体ではないためである。分岐を増やさずに済む。

#### ボトル（アルコール・6 段階）

| 段階 | 売価 | 原価 | 解禁 `tierPower` | 疲労係数 |
|---|---|---|---|---|
| 1 | 12,000 | 3,500 | 0.00 | ×1 |
| 2 | 35,000 | 10,000 | 0.25 | ×2 |
| 3 | 70,000 | 19,000 | 0.45 | ×3 |
| 4 | 110,000 | 30,000 | 0.60 | ×4 |
| 5 | 220,000 | 60,000 | 0.75 | ×5 |
| 6 | 400,000 | 105,000 | 0.90 | ×6 |

#### ボトル（ノンアルコール・3 段階）

未成年の担当客がボトルを注文したときの変換先。

| 段階 | 売価 | 原価 | 解禁 `tierPower` | 疲労係数 |
|---|---|---|---|---|
| 1 | 12,000 | 3,500 | 0.00 | なし |
| 2 | 35,000 | 10,000 | 0.45 | なし |
| 3 | 220,000 | 60,000 | **0.95** | なし |

**ノンアルは段階が粗く、解禁条件が重い。** 段階 3 はトーク 95 以上の未成年だけが
到達できる稀な達成であり、通常は 12,000／35,000 の 2 択に留まる。
これが年齢制限の実体である（4.3）。

#### 原価率について

ボトルの原価率を約 27% に設定している。現実のコンカフェ・キャバクラの
ボトル原価率はこれより低い（10〜20%）。**意図的に引き上げている。**

原価率が低いと高額ボトルの仕入れが実質ノーリスクになり、
「エース出勤日に合わせて高い酒を入れるか」という発注の判断が消える。
400,000 円のボトル 1 本＝原価 105,000 円は序盤の週売上の約半分にあたり、
売れ残りが痛手として機能する。

現実の原価率に寄せたい場合はここを下げてよいが、その場合は在庫のジレンマが
弱まるため、冷蔵庫の保管上限などで別途リスクを作る必要がある。

#### 発注できない品目（OB 差し入れ専用）

| 品目 | 原価 | 入手元 |
|---|---|---|
| アルコールボトル 段階 5・6 | 0 | 酒造メーカー OB が定期的に供給 |
| 期間限定商品（売価 2,000） | 300（実家の家業 OB なら 0） | イベント／実家の家業 OB |

酒造メーカー OB の価値は「最高段階のボトルを原価 0 で得られる」ことにある。
段階 5・6 は原価 60,000／105,000 円であり、資金の乏しい時期ほど効果が大きい。

### 14.3 給料（U-03）

時給 ＋ バック。日給ではなく時給で持つ。

```
時給 = 1,000 + (Talk + Regulars + Fame) / 3 * 7 + 勤続年数 * 100
日給 = 時給 × （シフト時間 − 深夜帯の時間 ＋ 深夜帯の時間 × 1.25）
バック = （チェキ ＋ キャストドリンク ＋ ボトル）の売上 × 15%
週給 = シフトごとの日給の合計 ＋ バック
```

| 状態 | 時給 |
|---|---|
| 新人（各パラメータ 20 / 勤続 0 年） | 1,140 円 |
| 中堅（各 50 / 勤続 2 年） | 1,550 円 |
| エース（各 100 / 勤続 5 年） | 2,200 円 |

**勤続 1 年ごとに時給が 100 円上がる。** 長く在籍したキャストは
それだけで人件費が重くなる。信頼度を積んで延命した相手は、
延命したぶん給料も上がっていく。

#### バックの対象を絞っているのが要点

**チャージと客のドリンクにはバックを付けない。** 席と時間の対価であり、
店の売上として扱う。バックが付くのはキャストが取ってきた
チェキ・キャストドリンク・ボトルだけである。

これによって、トークを伸ばすと**バック対象の売上比率そのものが上がる。**

| トーク | バック対象の比率 | 実効バック率 |
|---|---|---|
| 20 | 約 30% | 4.5% |
| 90 | 約 70% | 10.5% |

**エースの人件費は売上に連動して跳ね上がり**、
「育てれば育てるほど楽になる」という単調な構造にならない。

未成年は酒が売れずバックが伸びにくいため、自動的に安くなる。
年齢による給料テーブルの分岐を持たせない（分岐は年齢制限だけで足りる）。

### 14.3.1 営業時間とシフト（U-20）

| 項目 | 値 |
|---|---|
| 平日の営業 | 17:00〜23:00（6 時間） |
| 休日（土日）の営業 | 15:00〜23:00（8 時間） |
| 深夜割増 | 22:00 以降が対象。倍率 1.25 |
| 最短シフト | 2 時間 |

**シフトは「出勤するか」ではなく「何時から何時まで」で持つ。**
これがシフト表を判断の中心にする。

| 選択 | 得るもの | 失うもの |
|---|---|---|
| 長く入れる | 来客・売上・経験 | 疲労・給料 |
| 短く入れる | 疲労と給料の節約 | 売上と成長 |
| 深夜帯（22 時以降）に掛ける | 閉店までの売上 | 割増の人件費 |
| 休日に入れる | 2 時間ぶん多い売上 | 2 時間ぶん多い疲労と給料 |

来客・自然成長はすべて**出勤時間に比例する**。
平日フル出勤（6 時間）を 1.0 とした比で効かせているため、
4.1 の来客係数の校正はそのまま保たれる（**平日 18.0 人/日、休日 24 人/日**。T-44 で固定）。

**客はそのキャストのシフトより長くは居られない。**
2 時間シフトなら、トークが高くても滞在は 2 時間で打ち切られる。

#### ピークタイム（U-20 決着）

**作る。** `business.hourWeights` に時刻ごとの重みを持つ。

| 時刻 | 15 | 16 | 17 | 18 | 19 | 20 | 21 | 22 |
|---|---|---|---|---|---|---|---|---|
| 重み | 0.5 | 0.6 | 0.7 | 0.8 | 0.9 | 1.1 | **1.3** | **1.2** |

（15・16 時は休日のみ。平日は 17 時から）

無いと、シフトの時刻は「何時間か」と「深夜割増が掛かるか」しか意味を持たず、
**割増を避けて早番に寄せるのが常に正解**になる。それではせっかく時刻で
持っている意味がない。

**重みはその日の合計で正規化する。** したがって開店から閉店までのフル出勤では
来客数が変わらず、平日 18 人/日・休日 24 人/日の校正は保たれる。
変わるのは**部分シフトの取り分だけ**である。

| 平日 2 時間シフト | 来客の係数 |
|---|---|
| 17:00〜19:00（開店直後） | 0.250 |
| 21:00〜23:00（閉店前） | **0.417** |

**ピークは深夜割増（22 時〜）と重ねてある。** 重ねないと遅番が一方的に得になる。
実測では 20〜23 時のシフトは 17〜20 時に対して売上 +45% だが、給料 +14% に加えて
**疲労が増える**（疲労は接客した延べ時間に比例する、不変条件 26）。

> 稼ぎたければ混む時間に置く。ただし速く削れる。
> **疲れたキャストを早番に回して延命する**、という手がここで成立する。

これは U-07（モラルによる猶予）を却下した理由でもある。疲れたキャストを救う
手段はもう 1 つ増えているので、疲労限界そのものを緩める必要がない。

### 14.4 店長 AP（U-04）

| 項目 | 値 |
|---|---|
| 週次付与 | 10 AP |
| 特訓（1 パラメータ） | 3 AP / `baseGain = 6.0` |
| 悩み相談 | 2 AP / 疲労 −4.0 **かつ 信頼度 +4.0** |
| 面接（候補の上限値を見る） | 1 AP |

悩み相談が二重の効果を持つ。**目先の疲労を抜くと同時に、恒久的な貯金が貯まる。**
信頼度を 0 から最大まで積むには **25 回**の相談（50 AP）が必要で、
毎週 1 回続けても半年かかる。

**AP は店舗規模が大きくなっても増えない。** ここが「使い潰すか伝説にするか」の圧力源である。

キャスト 3 人なら全員に特訓が届く（9 AP）。12 人では届かない。
終盤に「誰を伸ばし、誰を諦めるか」を強制するのは AP の据え置きによる。
心理カウンセラー OB（回復量アップ）と出版関係者 OB（AP 不要の特訓本）は、
この不足を緩和する手段として設計に組み込まれている。

出勤による自然成長は `baseGain = 0.3 /日`。トークと知名度が満額、
モラルがその半分（`moraleWorkGainRatio = 0.5`、4.9）。

#### 集客は出勤では伸ばさない（U-19 決着）

`manager.regularsWorkGainRatio = 0.0` で据え置く。**集客は特訓でしか伸びない。**

現実には働けば常連が付くので、伸ばすほうが自然ではある。実際に開けて
週 3 日で 30 シードを測った。

| | 完走率 | 最終資金（平均） | 卒業/回 |
|---|---|---|---|
| 特訓のみ（採用） | 66.7% | 680 万円 | 5.7 |
| 出勤でも伸びる | **100.0%** | **1 億 3,364 万円** | 12.7 |

**資金が 20 倍になり、週 3 日の罰が完全に消えた。**

集客は「何人来るか」を決めるステータスなので、自然成長させると
売上 → 資金 → 設備投資 → 枠 → 売上 の輪が自走する。
そして**特訓の主な行き先が要らなくなるぶん、店長 AP の価値そのものが下がる**。
AP の据え置き（不変条件 7）が終盤の圧力源であることを考えると、
ここを開けるのは疲労限界を緩めるのと同じ種類の変更になる。

| ステータス | 伸ばし方 |
|---|---|
| トーク・知名度 | 出勤（0.3/日）＋ 特訓 |
| モラル | 出勤（0.15/日）＋ 特訓 |
| **集客** | **特訓のみ** |
| 酒耐性・ルックス | 特訓のみ |

### 14.6.1 信頼度と離脱（U-15）

```
k_careRecover      = 4.0     // 悩み相談 1 回の疲労回復
k_trustPerCare     = 4.0     // 悩み相談 1 回の信頼度上昇（25 回で最大）
k_trustRelief      = 0.35    // 信頼度 100 で疲労蓄積を 65% に抑える
k_warnRatio        = 0.75    // 限界値の 75% で予兆を出す
k_defectThreshold  = 55      // marketValue がこれ以上なら転生、未満なら飛ぶ
k_antiSpread       = 3.0     // 飛ばれたとき、他キャスト全員の Regulars を削る量
```

信頼度は**減衰しない**。貯金であり、一度積んだ関係は失われない。
減衰させると、ケアが「維持のための義務」になり、投資という性格が消える。

`k_defectThreshold = 55` は、集客・知名度・トークの平均が 55 という水準である。
初期値 20 前後のキャストは飛び、育成が進んだキャストは転生するようになる。
**育成の途中で離脱の質が切り替わる**位置に閾値を置いている。

#### 段階 5 の決着: 閾値 55 は分布の外にあった（U-15）

60 シードを通して、**転生は週 4 日で 0.3 回/run**（週 3 日・週 5 日では 0.0）
だった。飛ぶ側は 5.0 回/run あり、離脱の 94% が「飛ぶ」に寄っていた。
**「育てた者は引き抜かれ、育つ前の者は黙って消える」の前半が成立していなかった。**

原因は 2 つあり、両方を直した。

**1. 店長 AP が余っていた（U-13 で解決）。**
離脱は疲労限界の超過でしか起きず、転生と飛ぶはその**結果の分岐**でしかない。
AP は 10/週で悩み相談は 2 AP なので週 5 回ケアでき、キャスト枠は 3 人だった。
つまり全員を毎週ケアしても AP が余り、ケアが行き届いたキャストは
疲労限界に届かない。**育ったキャストほど離脱しない**状態になっていた。

設計の意図は「AP は有限なので全員に信頼は積めない、誰に投資するかが
終盤の中心的な判断になる」（6.2）だが、その**有限性が枠 3 人では発生しない**。
設備投資（14.9）で枠が 12 人まで伸びるようにしたことで、ケア不足
（疲労が限界の 75% を超えた人週）が 13 → 113 に増え、圧力が実際に生じた。

**2. 閾値 55 が分布の外にあった。**
疲労で離脱したキャストの `marketValue` を実測した。

| | P10 | 中央 | P75 | P90 | 最大 |
|---|---|---|---|---|---|
| 疲労離脱時の marketValue | 23 | 35 | 45 | 50 | 59 |

**55 は 99 パーセンタイル**である。閾値を分布の端に置いていたので、
転生が起きないのは当然だった。

**`k_defectThreshold` を 55 → 45 に変更する。** 転生は疲労離脱の **24.9%**、
週 4 日で 1.1 回/run になった。45 を選んだのは、**求人ティア 1 の
`capMean` と同じ値**だからである。

> 安く採ったキャスト（上限 45）は、どれだけ育てても marketValue が 45 に
> 届きにくいので**黙って消える**。求人費を積んで採ったキャスト（上限 60・75）は
> **引き抜かれる**。

**求人ティアの選択が、離脱の質そのものを決める**形になった。

閾値が分布の中でどこにあるかは `SweepTests.離脱時の市場価値の分布を測る` が
毎回検査する。中央値を下回ると転生が主流になり、95 パーセンタイルを超えると
転生が死ぬので、その両側で落ちる。

#### 素朴な自動プレイで出勤ペースごとに通してみた結果

段階 5 の通しシミュレーション（`SweepTests`）。**シード 60 本の分布**であり、

- **週 3 日**は売上が薄くて設備投資に届かない。枠が 9 人で止まり、

- **週 5 日**は疲労で離脱が**週 4 日の 3.4 倍**（8.0 → 26.8）に跳ね、

「使い潰すか、伝説にするか」がそのまま数字に出ている。

この形は `SweepTests` に固定してある。疲労・離脱・経費のどれかを緩めると
「週四日は多くのシードで完走できる」の上限側か、`AutoPlayTests` の
「働かせすぎると崩壊する」が落ちる。そのとき構造が残っているかを確認する。

この形は `SweepTests` に固定してある。

#### 求人費をケチることが最大の罠だった（段階 5 の発見）

段階 4 までの自動プレイは**常に最安の求人ティア（30,000 円）を使っていた**。
これを「素朴なプレイ」の基準にしていたが、分布を取ると基準が壊れていた。

| 求人ティア | 費用 | capMean | 完走率 | 最終資金 中央 |
|---|---|---|---|---|
| 1 | 30,000 円 | 45 | 22.5% | −33,743 |
| 3 | 200,000 円 | 75 | 100.0% | 9,983 万円 |

求人費 30,000 円は**家賃 1 週ぶん（70,000 円）にも満たない**。それでも
最安固定と上位ティアで完走率が倍以上違う。上限値 45 のキャストは
育てても固定費を割れる売上に届かないためで、**求人は節約する対象ではなく
投資する対象**である。

自動プレイの方針を「資金の 10% までで一番良いティアを選ぶ」に変えた
（`AutoPilot.PickRecruitTier`）。これはバランスの変更ではなく、
**測定の基準を直したもの**である。上の出勤ペースの表はこの基準による。

罠そのものは `SweepTests.求人をケチると完走できなくなる` に固定した。

「来客 1 人につきドリンク 1 杯」だった土台を、チャージ ＋ 時間制に
置き換えた（4.3）。客単価は **1,930 円 → 3,992 円**になり、
収支が反転した。

営業時間（平日 6 時間・休日 8 時間）、時刻で持つシフト、
時給 ＋ 勤続昇給 ＋ バック 15% まで入れた実測値。

素朴な自動プレイでも 10 年を完走し、一度も資金難に陥らない。

人件費は売上の 36% で、飲食業としては妥当な水準に収まっている。
仕入れ原価は 9%。**不足しているのは人件費や原価ではなく、それ以外の経費である。**

**要件の「赤字寸前のコンカフェ」から大きく外れている。**

バックを 15% に上げ、深夜手当と勤続昇給を入れても足りない。
人件費は売上の 34% で、飲食業としては妥当な水準に収まっている。

この時点では未決だった。上の「U-17 の決着」で経費を 3 本立てにして解消した。

#### 疲労

序盤（Tier 3 ＝ 限界 27 / 担当 6 人・日 / 酒 1.1 杯 / ボトル段階 1 が 0.13 本 / 酒耐性 20）。

```
日次 = 1.0 + 6×0.015 + (1.1×0.35 + 0.13×1×0.25) × 0.8 = 1.42
週 4 = 1.42×4 − 1.2×3 = 5.69 − 3.6 = +2.09 /週   → 約 13 週（3 ヶ月）で限界
週 5 = 1.42×5 − 1.2×2 = 7.10 − 2.4 = +4.70 /週   → 約 6 週で限界
```

出勤日数が直接寿命に効く。悩み相談（−4.0）を 2 週に 1 回入れれば週 4 は維持できる。

終盤のエース（トーク 95 / 酒耐性 90 / Tier 5 ＝ 限界 45 / 担当 40 人・日）。
`tierPower = 0.93` で全 6 段階が解禁され、ボトル期待単価は約 141,000 円。

```
日次 = 1.0 + 40×0.015 + (16.5×0.35 + 1.74×3.5×0.25) × 0.10 = 2.33
週 4 = 9.33 − 3.6 = +5.73 /週                     → 約 8 週で限界
```

**エースほど短命になる。** 接客数と酒量が増えるためで、酒耐性 90 でこれである。
酒耐性を伸ばさずトークだけで段階を上げると `sober` が跳ね上がり、さらに縮む。

#### 信頼度による延命

同じエースで信頼度だけを変える。

| 信頼度 | `trustRelief` | 日次疲労 | 週あたり純増 | 限界到達まで |
|---|---|---|---|---|
| 0 | 1.00 | 2.33 | +5.73 | 約 8 週（**2 ヶ月**） |
| 50 | 0.83 | 1.93 | +4.11 | 約 11 週 |
| 100 | 0.65 | 1.52 | +2.46 | 約 18 週（**4.2 ヶ月**） |

信頼度を最大まで積めば無ケアで 4 ヶ月持つ。ここに到達するには
悩み相談 25 回（50 AP、毎週 1 回で半年）が必要である。

そのエースの `marketValue` は 80 を超えるため、離脱時は**転生**になる。
予兆が 33.75（限界 45 × 0.75）で出るので、
信頼度 100 なら**予兆から限界まで 4 週以上の猶予がある**。気づけば間に合う。

一方、新人（各パラメータ 20 / `marketValue = 20`）は `k_defectThreshold` を
下回るため**飛ぶ**。そして予兆は出ない。
**育てた者は引き抜かれ、育つ前の者は黙って消える。**

#### 「ニシキ」（Tier 1 ＝ 限界 14 / 成長率 10 倍 / 酒耐性は成長 0）

```
特訓 1 回: 6.0 × 10.0 × (1 − 20/70) = 42.8   → 2 回で Cap 到達
寿命:    週 4 出勤で約 7 週 / 週 5 出勤で約 3 週
```

さらに**酒耐性が初期値のまま伸びない**ため、トークだけが跳ね上がって
`tierPower` が上がり、高額ボトルが解禁される。そして `sober` が下がらないので
その高額ボトルが疲労を最大効率で叩き込む。スキャンダル耐性 0 と合わせて、
**育ちきった直後に飛ぶか炎上する**レースになる。狙いどおり。

### 14.9 設備投資（U-13 決着）

要件 5.4 の 3 種。すべて `balance.json` の `facilities` にある。
**店長自身は育たない（不変条件 6）ので、店舗の強化はここだけである。**

| 設備 | 段 | 費用 | 効果 |
|---|---|---|---|
| 店舗拡張 | 1 | 3,000,000 円 | キャスト枠 3 → 6 |
| | 2 | 8,000,000 円 | 6 → 9 |
| | 3 | 18,000,000 円 | 9 → 12 |
| 冷蔵庫の拡張 | 0（初期） | — | 保管上限 240 |
| | 1 | 400,000 円 | 400 |
| | 2 | 1,000,000 円 | 560 |
| | 3 | 2,200,000 円 | 720 |
| エスプレッソマシン | 1 | 3,000,000 円 | 客のドリンク単価 +100 円 |
| | 2 | 9,000,000 円 | +220 円 |

#### 店舗拡張は「押すだけのボタン」にしない

1 段ごとに家賃が上がる。**この上乗せを 25,000 円 → 90,000 円に引き上げた。**

25,000 円では、増える 3 人が生む売上（週 50 万円規模）に対して誤差でしかなく、
拡張が「資金が貯まったら押すだけのボタン」になっていた。実際、
初期値のまま測ると最終資金の中央値が 2 億円を超え、週 5 日の使い潰し戦略まで
成立してしまった（枠が増えるので、潰した端から補充できる）。

90,000 円にすると最大まで広げた時点で家賃が **70,000 → 340,000 円/週**になる。
これで「広げたが埋められない」という失敗が成立する。実測でも、設備投資ありの
ほうが最終資金の中央値は高い（3,950 万 → 6,320 万）が、**P10 は下がる**
（2,707 万 → 1,588 万）。**上振れと引き換えに下振れを買っている。**

#### 冷蔵庫は店舗拡張の前提になる

保管上限はドリンク（ソフト・アルコール）とボトルに掛かる。
チェキフィルムと期間限定商品は冷蔵しないので数えない。

容量は**週次の実需の実測値**から決めた。

| キャスト枠 | 週に要るドリンク（実測の最大） | 賄える冷蔵庫の段 |
|---|---|---|
| 3 人 | 198 | 0（240） |
| 6 人 | 335 | 1（400） |
| 9 人 | 440 | 2（560） |
| 12 人 | 544 | 3（720） |

**各段はちょうど 1 つ下の枠数までしか賄えない。** 枠だけ広げると在庫が
入りきらず、機会損失と固定客の喪失（U-05）を招く。2 つの設備が
噛み合っている必要がある。

上限を超える発注は**黙って切り詰めずに拒否する**（`ActionResult.NoStorage`）。
切り詰めると、枠を広げたのに仕入れが足りない状態にプレイヤーが気づけない。

なお **OB の差し入れは上限を見ない。** 発注ではなく届きものなので、
冷蔵庫が一杯だから受け取れない、という形にはしない。

#### エスプレッソマシンは人件費に跳ねない唯一の投資

客のドリンクの単価だけを上げる。**チャージには効かない**（席と時間の対価で
あって商品ではない、4.3）。そして客のドリンクは**バックの対象外**
（不変条件 25）なので、売上が伸びてもキャストの給料が増えない。

| | 売上への効き方 | 人件費 |
|---|---|---|
| トークを伸ばす | 滞在時間が伸びて全項目が増える | **上がる**（実効バック率 4.5% → 10.5%） |
| エスプレッソマシン | 客のドリンクの単価だけ | 変わらない |

**エースを育てるほど人件費が売上に連動して跳ね上がる**のが設計の要点
（14.3）なので、そこから外れた売上の伸ばし方を 1 つだけ用意した形になる。
一方で効果が店の規模に比例するため、**序盤に買っても回収できない**。
枠 12 人で週の延べ滞在が 1,500 時間を超えてはじめて割に合う。
